# HOMESTEAD 98

**A pre-rendered isometric farm, lit in real time.**

No Blender. No modelling files. No third-party runtime libraries. Every sprite,
material, pattern, glyph and shader in this repository is generated by the code in
this repository.

<p align="center">
  <img src="docs/img/indoor-timelapse.gif" width="640"
       alt="A full day inside the farmhouse: sunlight moves across the floor as the clock runs from dawn to dusk.">
</p>

<p align="center"><em>A full day in the farmhouse. The camera never moves — only the clock does.</em></p>

The sprites are baked offline as hard pixels: nearest-neighbour, integer-aligned,
banded. The lighting is not. It is a continuous field, lower in frequency than the
pixel grid, multiplied over the top at runtime. So the silhouette stays crisp while
the light breathes — the sun crosses the sky, shadows rotate, a lantern actually
lights the wall it hangs on, and **sunlight comes through the windows and moves
across the floor as the day passes**, carrying the colour of the glass it came
through.

</p>

## Try it

```bash
npm run build     # pre-render both atlases — about 4 seconds, no dependencies
npm run serve     # static server on http://127.0.0.1:8123
```

Or build one self-contained file and just open it:

```bash
npm run single    # -> dist/homestead98.html  (2.99 MB, every module + both atlases inlined)
```

Running the game needs nothing but a WebGL2 browser. `build`, `serve` and `single`
use only Node built-ins, so **`npm run build` works on a fresh clone with no
`npm install` at all.** Puppeteer is a devDependency for the screenshot and
end-to-end tools, and nothing else.

## The one-line thesis

> **Make the light lower-frequency than the pixel.**

## What is actually unusual here

**1. The depth buffer is free, because the depth was already in the pixels.**
Sprites write real per-pixel depth, but nothing extra is baked to supply it. `nrm.a`
already stores the world height of the surface each texel draws, and the projection
is orthographic and invertible, so depth falls out in closed form:

```
dep = (x + y) + (2·HH / ZPX) · z
```

`x + y` drops straight out of the projection, so it never has to solve for x and y
at all. Two lines of fragment shader buy a real 24-bit depth buffer over all
geometry, for zero extra bytes of asset. Everything that used to be a sorting
problem — "the bed's foot is eaten by the wall", "the rug draws over the table" —
becomes a geometry problem instead. **→ §2**

**2. Zero runtime dependencies, down to the file formats.**
`tools/lib/png.mjs` is a hand-written PNG encoder *and* decoder. `tools/lib/pack.mjs`
is a shelf packer. The software rasteriser, the bitmap font, the static server and
the single-file bundler are all in here. Nothing is vendored, nothing is fetched,
and the atlases are packed by code you can read in 93 lines.

**3. Sunlight through a window is a 3D-DDA over a voxel transmittance volume.**
Not a fixed-step march — a fixed step either leaks light through walls or crawls.
Each window opening is a hole in a sealed box, and the shape of that hole is what
decides where the light lands and how far it throws. Stained glass gets its colour
from per-voxel transmission, so five colours need no new shader. **→ §5**

**4. Failures fall in the safe direction, and say so.**
An earlier version ghosted interior walls using a per-pixel focus map. It worked
beautifully — right up until the map failed to generate, at which point every
cut-away wall silently turned solid and swallowed the furniture behind it, with
nothing in the console. That is the worst kind of failure: silent, total, and it
looks exactly like "the depth system is broken". Now the interior does not depend
on the map at all, the shader has a fallback branch, and the renderer counts frames
without focus and warns you by name that you are probably running a stale module.
**→ §1**

`npm run verify` is the honest one. It boots the game, renders, and then *measures*:

interior, that a villager behind a building is revealed **and that only the 1.3% of
the facade actually in front of them fades**, that ghosted walls still block the
sun. It fails loudly rather than producing a plausible screenshot of a broken
build.

# 中文技术文档

以下是最初的工程记录，保留了写作时的原始语气和编号（§1–§15），英文部分提到的
章节号指的就是这里。原文是一个**纯代码实现**的网页版等距（2:1）种田游戏：
没有 Blender、没有建模文件、没有任何第三方运行库。

核心命题只有一句：**让光比像素低频。**

**遮挡不再是画家算法。** 精灵自带逐像素深度——不是额外烘的一张深度图，而是
从投影里反解出来的（见第 2 节）——写进一个真正的深度缓冲，由 GPU 逐像素裁决谁
盖住谁。所有「床尾被墙吃掉」「地毯压在桌子上」这一类问题因此从**排序问题**变成

**运行游戏只需要支持 WebGL2 的浏览器。** 离线渲染器与服务器只用 Node 内置模块。

## 1. 遮挡：把「挡镜头」和「挡太阳」拆开

这一版最重要的改动不是加了什么，而是**拆开了一个被混在一起的判断**。

挡住镜头的东西，和挡住太阳的东西，不是一回事：

| | 相机看不见它 | 太阳被它挡住 |
| --- | --- | --- |
| 近侧墙 | 是 | 是（墙就是墙） |
| 窗外的一棵树 | 不是 | 是 |
| 玩家身后的谷仓 | 是 | 不是（光从另一侧来） |

旧版本用**同一个标记**回答这两个问题，于是三件事同时坏掉：为了看得见房间，
近侧墙被削成 36 厘米的矮裙、天花板只盖后半间让阳光从缺口灌进来；结果是地板中间
横着一道巨大的硬边阴影、能接光的窗户全都长在看不见的墙上、光斑正好落在墙自己
遮住的那一条地板上。

现在两件事各归各的：

```
相机 → 焦点深度图（src/main.js addFocus）→ 逐像素深度比较（SPRITE_FS）
                                              ↓
                                    光照 pass 两层着色后合成
太阳 → 体素透射率体积（src/interior.js marks）→ 3D-DDA 步进（LIGHT_FS roomMarch）
```

**被透明化的墙仍然是墙。** 它照常写进体素体积、照常投影、照常被 AO 烘焙、
照常在高度场里留戳记 —— 只有「画不画、画多淡」变了。这是一条底层规则，
之后所有建筑都走它。

### 谁该透明：室内是**声明**的，室外才是**推断**的

#### 室内：房间自己知道答案

投影是固定的（眼睛永远在 +x+y 上方），所以「哪两面墙挡着相机」是**房间的属性**，
不是相机的属性，也不是玩家在看什么的属性。布置房间的那段代码本来就知道哪条是
+x 边、哪条是 +y 边——所以它直接说出来：

```js
const CAM_SIDE = { '+x': true, '+y': true, '-x': false, '-y': false };
place(front, i, h - 1, 0, null, 0, { cut: CAM_SIDE['+y'] });   // +y 那一条
place(right, w - 1, j, 3, null, 0, { cut: CAM_SIDE['+x'] });   // +x 那一条
```

挂墙件同理：`wall(id, i, side)` 已经知道 `side`，于是挂在 +x / +y 上的窗帘、挂画、
挂钟跟着那面墙一起淡出，挂在另外两面墙上的不动。

**室内因此完全不发焦点图。** 渲染器看到「没有焦点」，走整块淡出的分支，墙就按声明
淡出。这条路没有可以失败的地方。

#### 室外：焦点图，逐像素

室外要回答的是另一个问题：「有人被这栋楼挡住了吗」。这里的焦点是一组世界空间盒子
——每个村民一个（宽度是他们占的格，高度是他们的身高），加上鼠标下的地块——先被
光栅化进一张半分辨率的深度图，深度测试天然保留每个像素上最近的那个焦点表面。
然后每个精灵像素拿自己的深度去比：

> **一个精灵像素变透明，当且仅当它比「相机必须看见的东西」在该像素上的最近表面
> 还要近。**

于是农舍屋顶上会出现一个和村民一样大的窗口，而不是整栋淡出。

#### 失败必须往安全的方向倒

这一版真正学到的东西在这里。

上一版**室内也用焦点图**。它工作得很好，直到焦点图没有生成——一个过期的模块、
一个半更新的页面、一次重建中的刷新——于是每一个 `cut` 出来的墙都悄悄变成实体，
连带把它后面的家具全部吞掉，而控制台里一个字都没有。**这是最坏的一种失败：
静默、彻底，而且看起来就像"这个深度图系统没写好"。**

现在有两道防线：

1. **室内不再依赖它**（见上）。声明的东西不会因为一张图没画出来而消失。
2. **着色器有兜底分支**。`u_focusOn == 0` 时不做逐像素比较，直接按整块淡出——
   细化是奢侈品，淡出才是必需品。一段被声明为「该让路」的墙，无论有没有那张图，
   都会让路；焦点图只决定它**哪些像素**让。
3. **失败会被说出来**。渲染器数着「已经多少帧没有收到焦点了」，超过 90 帧就
   `console.warn`，直接点名「你多半在跑一份过期的 `src/main.js`，请 Ctrl-Shift-R」。
   `tools/probe-stale.mjs` 会把这条路径跑一遍。

#### 为什么清成「最远」而不是 0

焦点图用线性过滤采样（这样幽灵边界有两像素的柔化），而它的空像素清成**深度范围
的远端**，不是 0。清成 0 的话，混合会把 0 掺进真实深度里，让焦点盒子**外面**那一圈
比盒子里**更**急于变透明——正好反了。清成远端，混合只可能更保守。

同样地，深度在编码前要先加一个**原点**：深度是 `x + y + K·z`，在地图近角之外是
**负数**，而焦点盒子允许挂在图外。直接编码会把负数夹到 0，读回来就成了「这里没有
焦点」——房间的靠外一半会悄悄不再保护自己。这两个都是靠 `--lightdebug 9` 看出来的。

### 为什么是 alpha，不是「不画」

第一版是**有序抖动镂空**（在 G-buffer 里假装透明），一次 50% 的屏幕门抖动罩住
一整个房间就是一片噪点，而且图案钉在屏幕上，相机一动就爬。

第二版是**干脆不画**，也就是等距室内的通行做法。它看起来对，但它把墙从光照里
一起删掉了——这正是漏光的来源。

现在是第三种：被遮挡的精灵写进**第二个、带 alpha 的 G-buffer 图层**。光照 pass
把它当作一个正常的表面来着色（用墙自己的世界坐标、自己的法线），然后按 alpha
合成到房间上。墙还在，你只是能看穿它。

顶部的 alpha 会被抬高一档（`SPRITE_FS`），所以压顶线和房间轮廓始终清晰：
均匀淡出的墙是一团污渍，守住轮廓的墙才读得出是「剖切」。

**变透明的是像素，不是整块精灵。** 在室外，一栋楼只有真正挡着人的那一小块会淡出
（屋顶上一个村民大小的窗口），其余部分照样实心——这不是「这块要淡、那块不淡」的
二选一，是逐像素的深度比较。

### 剖切开关：通透，还是看得见墙

挡在相机前面的那两条墙边怎么处理，是一个**三态开关**，`K` 键循环，
脚本里是 `game.cutaway`：

| | 效果 | 用在哪 |
| --- | --- | --- |
| `ghost` | 淡到 24%，只留一条轮廓线（默认） | 日常：看得见房间，也读得出墙在哪 |
| `hide` | **整条墙边连同它上面的窗、门、窗帘、挂画一起不画** | 想直接看等距室内，不要任何遮挡 |
| `off` | 全部画实 | 想看这栋房子本来的样子 |

**它基本上只动相机，不动光 —— 有一个例外，而且它正好落在近侧那条地板上。**

近墙照常站在室内透射率体积里（太阳照样过不去），窗洞照常按自己的形状切分地板上的
光斑：**透射率体积、太阳直射项、窗洞形状在三种模式下逐位相同。** 但 `src/main.js`
送给渲染器的一个数字是跟着这个开关走的：

```js
shaftAmount: shaftAmountOverride ?? (state.cutaway === 'ghost' ? 0.28 : 0.18),
```

空气散射（§6 那束光轴）的强度：`ghost` 0.28，`hide`/`off` 0.18。也就是说
**"隐藏近侧墙"这个名字底下混了一次光照改动**——切到 `hide` 不只是不画那两面墙，
还把那束光调弱了 36%。同机位、同时刻、同样 `hide`，只把这一个数字改成 0.28：

```
game.shaftAmount = 0.28          # 别的什么都不动
node tools/diff-rect.mjs 250,235,150,45   # 近侧带
  → 1156/6750 px differ (17.1%), mean delta 15.6
node tools/diff-rect.mjs 250,120,120,45   # 房间中段
  → 100/5400 px differ (1.9%),  mean delta 5.3
```

这个例子也说明为什么下面这条旧证据量出来是"0 像素差异"：取样框 `250,120,120,45`
在房间中段，那里的光轴本来就只有 1.3（见 §6 的表），挪到近侧带就是 17% 的像素不一样。

**所以"只动相机不动光"是一条应该成立、但现在被一个数字破坏的不变量。**
把它改成常数（`?? 0.28`）就真的成立了——见 §13 第 1 条。在那之前，做 A/B 对比
（剖切、隐藏、任何"只改画面"的开关）时请把 `game.shaftAmount` 钉死，否则你比较的
是两张光照不同的图。

### 按类别隐藏：另一件事

`hide` 开关按**是什么**关掉某一类零件——窗和墙都是 `cat: 'wall'`，灯和桌子都是
`cat: 'furn'`，所以按类别给的开关说的是人指着一件东西说得出口的话：

| role | 包括 | 快捷键 |
| --- | --- | --- |
| `window` | 三种窗 | `N` |
| `lamp` | 吊灯 / 油灯 / 蜡烛 / 提灯 | `L` |
| `curtain` | 窗帘 | `M` |
| `hang` | 挂画 / 挂钟 / 壁架 | `J` |
| `door` `wall` `roof` | 门 / 墙 / 屋顶 | 脚本 |

```js
game.hide.lamp = true;    // 台灯、吊灯、蜡烛、提灯一起消失
game.hide.window = true;  // 四面墙上的窗一起消失（包括你看得见的那两面）
game.roles;               // 当前场景里有哪些 role、各多少个
```

和 `cutaway` 的区别：`hide.window` 把**四面墙**的窗都拿掉，`cutaway = 'hide'` 只拿掉
你看不见的那两面墙**连同它们上面的窗**。想看一个没有遮挡的房间，用后者。

隐藏不是淡出：被隐藏的东西**根本不画**，不遮挡、不参与光照、不花任何代价。
`--hide lamp,window` / `--cutaway hide` 可以在截图工具里直接试。

**隐藏窗不等于关掉光。** 窗洞在体素体积里是另一套数据（`b.solidBox/glassBox` 声明的），
隐藏只影响相机看到的东西——阳光照样从那个洞进来。第 1 节开头那条规则在这里同样成立。

## 2. 深度缓冲：谁盖住谁

室内最初看起来「床尾被墙吃掉」「书柜被墙切一半」，那不是摆放错了，是**排序键错了**。

当时的修法是给每件东西算一个排序键（front-most geometry 的前沿），把场景按它排一遍
再按顺序画。那个修法对了很多东西，但它治的是症状：**画家算法是把一个偏序硬压成
全序**，两个在屏幕上重叠、在深度上交错的物体，不存在一个「谁先画」的正确顺序。
于是每加一件家具、每改一次布局，都是在赌这一版的前沿键还成立。

### 深度图不用存，它本来就在

关键不是「加一张深度图」，而是发现**深度图已经隐含在已有的数据里**。

`nrm.a` 每个纹素存着这个纹素所画表面的世界高度。投影是正交等距的、可逆的：

```
screen.x = (x - y) · HW
screen.y = (x + y) · HH − z · ZPX
```

所以「屏幕像素 + 高度」唯一确定世界坐标，而沿视线方向的深度是一个闭式：

```
dep = (x + y) + (2·HH / ZPX) · z
```

而且 `x + y` 直接从投影里掉出来，不需要真的解出 x 和 y。于是 `SPRITE_FS` 里两行：

```glsl
float xpy = (rel.y + worldZ * u_iso.z) / u_iso.y;   // 就是 x + y
gl_FragDepth = (xpy + u_depthK * worldZ) / u_depthRange;
```

一个真正的 24 位深度缓冲，逐像素、对全部几何生效，**没有多花一个字节的资源**。

### 谁赢了这场赌局

| | 画家排序 | 深度缓冲 |
| --- | --- | --- |
| 谁盖住谁 | CPU 上一个数 | GPU 逐像素比较 |
| 交错几何（一半在前、一半在后） | 不可能表达 | 自动正确 |
| 地毯 vs 它垫着的桌子 | 要靠场景声明 | 地毯在 z=0，桌子在 z=0.875，桌子赢 |
| 吊灯 vs 桌子 | 要靠场景声明 | 吊灯在 z=2.15，吊灯赢 |
| 两件前沿完全相同的东西 | 靠稳定排序的运气 | 深度真的相同才轮到顺序 |

`under` / `over` 因此退化成了**平局裁决**（排序键上 ±0.01，而排序键本身量级约 10；
深度上各加 +0.01 的前向余量），不再是「永远最先画 / 永远最后画」。
它们现在只做两件事：给恰好共面的东西定个先后（铺在地板上的那块地毯），
以及**记录一件东西真实的离地高度**。

两个余量都是**正的**，这一条值得写下来，因为「`under` 应该给个负余量」是
最顺手、也最坑的写法：一块和地板**严格共面**的地毯深度差是 0，负余量会把胜负
判给地板，地毯就消失了。地毯铺在地板上就该赢地板 —— 那是「铺在」的意思；
它输给站在它上面的桌子，靠的是 0.9 个单位的真实几何，不是任何余量。

### 站在别的东西上面，就说出来

桌灯原来是照着地板到桌面的高度建模的（0.90 单位，而桌子高 0.88、墙高 2.2），
再靠 `over` 画在桌子上面。它**看起来**像一盏桌上的灯，几何却在桌子里面 ——
偶然对，而且是深度缓冲接管后第一个坏掉的东西，因为「谁近谁赢」不接受商量。

现在场景直接说：

```js
over(oil_lamp, 4, 4, 0, TABLE_TOP);   // 站在桌面上，离地 0.88
```

灯被抬到它真正站着的高度（屏幕原点跟着上移，高度区间跟着上移），深度因此是诚实的。
抬高之后它变成了 1.78 单位高的火炬、顶上 1.93 还有一盏吊灯 —— 所以**改的是模型**：
它被缩成 0.60 倍，成为一盏真正的桌灯。**没有靠调偏移量去糊。**

另外两处层级细节：

* **挂墙的东西跟着墙一起淡出。** 窗帘按类别是家具，可视觉上它是墙的一部分 ——
  墙淡成 24% 的薄膜而窗帘保持全强度，结果就是一块亮斑浮在你想看清的房间里。
  所以 `furn_curtain / painting / clock / shelf_plates` 在模型描述符里显式写了
  `cut: true`：挂在墙上的东西和那面墙同进退。
* **幽灵墙只保留一条两像素的轮廓线。** 原来是「顶部半格抬高 alpha」，
  于是被太阳照亮的压顶板和窗帘成了画面里最亮的东西。现在只在最顶端
  `z1-0.10 .. z1-0.015` 这一条抬高 alpha —— 你仍然知道墙在哪，但它不再抢戏。

## 3. 室内：独立场景 + 独立分辨率

第一版把室内的墙拆成瓦片铺在户外地图上，靠剖切看进去。那个做法是错的，而且错在三处：

* 一栋 8×6 的房子硬塞进 44×44 的户外构图里，把农场布局整个压坏了；
* 房间被绑在世界的 **32 px/格** 上，太小、看不清——室内本来就是"小、近、细"的空间，
  它需要的像素预算和户外完全不同；
* 剖切规则随相机移动而变化，同一个房间在不同帧里长得不一样。

**所以室内是一个独立的场景，用自己的分辨率。**

```
户外   64×64 格，32×16 px/格   —— 宽阔的山谷、农场、树林
一层   11×9  格，48×24 px/格   —— 起居室：炉膛、厨房、床龛、餐桌
二层   9×7   格，48×24 px/格   —— 阁楼：楼梯口、床铺与摇篮、书桌
礼拜堂 15×11 格，48×24 px/格   —— 中殿 + 双侧廊 + 圣坛：列柱、彩窗、玫瑰窗
```

四张地图（一张户外、三张室内）、两套图集、两套投影。切换集中在 `enter()` 一个函数里：
投影、图集、高度场、体素体积、相机一次全换。于是谁都不用为对方妥协——户外那栋房子
就是一栋漂亮的房子，而室内拿到了它需要的像素。

`U` 键（或 PageUp/PageDown）按 `STOREYS = ['indoor','upstairs','chapel']` 循环，
`SCENES` 是唯一的场景表。加第三张室内图没有动到引擎里任何"场景"概念：它只是
`src/interior_chapel.js` 里的一份图纸 + `tools/models/chapel.mjs` 里的一批新模型。

### 一层和二层是两个场景，不是两块楼板

这个房子的楼层是**独立场景**，各自有自己的透射率体积、自己的剖切声明、自己的
相机中心。这样做的理由不是偷懒：剖切、焦点体积和光照体积在这个渲染器里全部是
「**从一个固定相机看一个房间**」的陈述，把楼层塞进一个场景意味着它们每一个都要
先学会「楼层」这个概念——而它们不需要。第三张室内图（礼拜堂）是同一句话的第三次
验证：它比前两张都大、墙高是前两张的两倍，但它要做的仍然只是"声明一个房间"。

代价只有一处：体积纹理不能共用。`renderer.buildVolume()` 原先只有**一个**纹理槽，
第二次调用会把第一份 `deleteTexture` 掉——二层一建，一层的室内光照就废了。所以
现在每个场景持有自己的一份（`makeVolume` 建、`useVolume` 切、`renderer.volume`
是当前这份），上下楼只是换一次绑定，不重建、不上传，也碰不到你离开的那一层。

**一层的地图没有因为二层而改动任何一个字。** 这不是承诺，是可测量的：
把一层渲染成帧，与加二层之前的基线逐像素对比，差异是 1.3（比对方法自身的噪声底）。
`tools/check-interior.mjs` 也不变地跑在同一份图纸上。

**加礼拜堂之后，这条仍然是可测量的，而且量得更狠了。** 三层改动一起做完之后再测：

| 对比 | 结果 |
| --- | --- |
| 图集逐精灵像素比对（`work/dsh-sprite-diff.mjs`） | 261 个旧精灵**全部逐像素相同**（另有 52 个新精灵） |
| 一层正午渲染，旧源 vs 新源 | 亮度均差 **1.5**（噪声底 1.2） |
| 一层日出渲染（低太阳，最能暴露光照改动） | **1.5** |
| 二层正午渲染 | **1.3** |
| `check-interior` 图纸核对 | 一层 84 件/219 标记、二层 67 件/164 标记，连"6 格走不到"的清单都逐字相同 |

图集是**货架打包**的：加模型会把每个精灵矩形重新排一遍，所以"看起来没变"这句话在
这里必须落到像素上，而不是落到清单上。

**同一份模型代码，渲染两遍。** 室内资产不是重写的，是 `setScale(1.5)` 把房间套件、
家具和礼拜堂新模型在 48 px/格下重渲了一次（`tools/build-assets.mjs --set interior`）。

室内没有屋顶精灵——天花板是**体素体积里的一块实心板**。这就是房间足够暗、
窗户才显得重要的原因。

### 第三张室内图：礼拜堂

第三张图不是"再来一间屋子"，是拿整套管线去撞一次它没撞过的东西。选礼拜堂，是因为
它同时压到四件这个项目一直没试过的事：

* **15×11 格、墙高 4.2**（民居是 2.2）。这是第一间比视口还大的房间，也是第一次
  让"墙有多高"变成一个必须写在图纸里的数字（`CHAPEL_H === CH`，`check-interior`
  会拿摆放好的墙件去核对天花板盖在哪，差 0.02 就报错）。
* **十根独立列柱**。柱子是 `cat: 'wall'`，所以它**进体积**：阳光从右廊彩窗进来时会被
  柱列打断，在地面上梳出条纹。这是这间屋子读起来像"建筑"而不是"壁画"的最大原因。
* **彩绘玻璃**。`glassBox(..., {trans, tint})` 从体积系统第一天就在，但直到礼拜堂
  之前，全项目每一处调用传的都是同一个暖白：`[1.0, 0.955, 0.86]`。tint 不是装饰，
  它是**逐体素的颜色**，光每穿过一格就乘一次。五种玻璃＝地面上五条不同颜色的光带，
  外加空气里同色的光柱——不需要新着色器、新 pass、新 uniform。
* **圣坛 + 玫瑰窗 + 马赛克地面**。平面按"哪面墙能晒到太阳"来排：`+x/+y` 两run
  放三联大窗（太阳整天在这一侧），`-y` 后墙正中放玫瑰窗配四扇尖窗，`-x` 侧廊放三扇。
  合唱席铺马赛克，中殿铺深浅相间的大理石，侧廊素面。

新资产在 `tools/models/chapel.mjs`：石墙（带盲拱）、尖窗（五色铅条）、三联大窗、
玫瑰窗、西门、列柱、两种大理石与马赛克地面、长椅、圣坛、读经台、洗礼盆、烛台、
挂幡、系梁桁架。全部沿用 roomkit 的墙约定（`+y` 边、rot 0..3），所以图纸那边
写起来和民居完全一样。**引擎侧只多了两处**：`finishRoom(kit, {wallH})` 让天花板高度
变成图纸的参数，以及相机夹取范围改成"房间越大、可平移越多"（见 §13）。

一个细节值得写下来，因为它是"资产适配引擎"而不是"引擎迁就资产"的例子：玻璃在模型里
只有 5 cm 厚，而室内体素是 7 cm，所以光栅化会把它放大到两格，光穿过时 `trans` 和
`tint` 各乘两次。于是 `GLASS` 表里的数字是**地面应当收到的东西的平方根**（0.84 而
不是 0.71），五种颜色也就成了半强度原色。这不是妥协，是把量纲写对。

## 4. 室内：一间真正的、被封起来的房子

房间是 **11×9 格、四面全高墙、八扇窗、一道门、以及一整块天花板**。

这不是排版偏好，是上一节那条规则的直接后果。旧版本不敢封顶，是因为一封顶，
阳光就只能从窗户进来，而窗户在近侧墙上、光斑落在墙自己遮住的那条地板上 ——
**房间封死，阳光就落在你看不见的地方。** 现在近侧墙会为相机透明化，那一条地板
看得见了，于是封顶不再有任何代价。

于是室内第一次成为物理上正确的暗室：

* 天花板是体素体积里的一块实心板，盖满整个房间；
* 墙壁进体积，**家具不进**（见下）；
* 直射阳光只有一条路进来：穿过某个窗洞。光斑因此是房间里最亮的东西；
* 补光来自**门户光源** —— 每扇窗内侧 0.55 单位处一个点光源，强度按这扇窗
  朝向太阳的程度缩放，颜色取天空色混一点阳光。所以房间的补光本身跟着一天走。

### 窗洞尺寸是布光的主旋钮

```
throw = 窗台高度 / tan(太阳高度角)
```

正午 58°，光斑几乎是贴着墙的一条；清晨 25°，同一扇窗把光带甩出三格远。
所以四面墙都有窗 —— 太阳从日出到日落扫过四分之一圈罗盘：+x 吃早晨、+x+y 吃
正午、+y 与 -x 吃傍晚。**哪一面墙没有窗，哪一面墙就让一天里的三分之一是黑的。**

而且三种窗，每一种在一天里留下不同的斑：

| 窗型 | 开口（格 · 单位） | 用在哪 | 光斑是什么形状 |
| --- | --- | --- | --- |
| `wall_window` 平开窗 | x 0.06–0.94 · z 0.62–2.02 | 背光的 -x / -y 墙 | 一条 |
| `wall_window_tall` 落地窗 | x 0.05–0.95 · z 0.28–2.06 | 迎光的 +x / +y 墙 | 又长又宽的一条 |
| `wall_window_arch` 拱窗 | x 0.08–0.92，圆头 | 每面墙各一扇 | **一个拱** |

拱窗的圆头不是画上去的：它由 14 根竖列拼出来，每一列同时声明自己的玻璃
（透光）和头顶的实墙（挡光），**所以落在地板上的光斑真的是拱形的**。
一扇窗的形状能一路走到地板上 —— 这是让四面墙读起来像四面墙最便宜的办法。

迎光墙才吃得到直射，所以把落地窗给它们：窗台从 0.62 降到 0.28，光斑的落点距离
直接翻倍，进光量也差不多翻倍。这是室内变亮的主要原因 —— **不是靠调曝光，
是靠把洞开大**。

窗洞几何在 `tools/models/roomkit.mjs` 顶部，几个数字决定一切。

### 家具摆放是一份图纸，不是撒点

六个功能区，全部靠墙或成组，中间留出两条通道（第 y=2 行与第 x=6 列）：

```
后左   灶台区  壁炉 / 大锅 / 木桶 / 拉过来的摇椅
后中   洗涤区  案台 / 奶油桶 / 炉子 / 提灯，门边靠一张画
左     卧铺区  床 / 床头柜 / 木箱   （(0,2) 与 (0,5) 留给左墙的两扇窗）
中     餐桌    圆毯（under）/ 2x2 桌 / 三把椅子 / 桌上的油灯 / 吊灯（over）
前左   阅读角  书柜 / 小毯 / 扶手椅 / 盆栽
右     储藏    衣柜 / 五斗柜 / 长凳 / 蜡烛
```

三层规则，一层比一层更靠上：

1. **渲染层：不用管了。** 叠放、交错、一半在前一半在后，全是深度缓冲的事。
   图纸只需要说「这件东西站在桌面上，离地 0.88」（`over(..., TABLE_TOP)`），
   不需要说「它应该画在桌子后面还是前面」。
2. **图纸层：墙前面那一格必须空着。** 上一版扶手椅正正停在书柜前面 —— 遮挡是对的，
   家具是废的。任何靠墙的东西，它正前方那一格到地面都必须是空的。
   这条**不会**被深度缓冲救掉，因为它管的是可见性，不是遮挡。
3. **图纸层：挂件要挂在挂得住的墙上。** 窗不是墙：画靠着窗、挂钟挂在书柜身体里，
   这两种错俯视图永远看不出来。

`tools/check-interior.mjs` 把第 2、3 条也一并检查：footprint 重叠、有没有
家具站在地板外、从门口能不能走遍、挂件是否挂在窗上、正前方有没有更高的东西挡住它。

```
node tools/check-interior.mjs
  interior ground 11x9: 84 objects, 219 volume marks
  walkable tiles: 65, reachable from the door: 59  ** 6 stranded: 2,0 8,0 9,0 10,0 10,5 10,6 **
  no overlaps, nothing outside the floor

node tools/check-interior.mjs --storey upper
  interior upper 9x7: 67 objects, 164 volume marks
  walkable tiles: 36, reachable from the door: 36  OK
  no overlaps, nothing outside the floor
```

（一层那 6 格是右墙那一列本身：墙不算占用格，所以它们会以「走不到的空地」
出现在统计里。这是地图记账的口径问题，不是布局问题。工具现在会**点名**这些格子，
而不是只报一个数字——「6 格走不到」没法行动，「(7,2) 被摇椅、五斗柜和长凳围死了」
可以。二层就是靠这句话改到 36/36 的。）

摆放代码里所有坐标都是**「这件家具占哪几格」**：旋转过的精灵仍然绕未旋转
footprint 的中心旋转，所以 `place()` 会把非正方 footprint 的锚点补回半格 ——
否则一把转过 90° 的长凳会偏半格，而且只在转过之后才偏。

## 5. 阳光真的穿过窗户：一根光线的两个阶段

一个**高度场表达不了「洞」**——它只能回答「这个高度以上有没有东西」，
所以它永远无法让光穿过竖直墙面上的窗户。解法是给室内单独建一个
**3D 透射率体积**，每个体素存：

```
R   = 透射率      0 = 实体墙，255 = 空气，中间值 = 玻璃
GBA = 穿过它时被染上的颜色
```

体素不是另写一份数据，而是**由生成精灵的同一份模型代码声明的**：
`b.solidBox()` 建几何的同时声明「这里挡光」，`b.glassBox()` 声明「这里透光且染色」。
精灵和光照体积因此不可能对不上。

### 3D-DDA：为什么固定步长一定会漏光

原来的写法是「沿 z 每步固定高度、用三线性采样取体素」。它有一个致命性质：
**每步在水平方向前进的距离是 `|dir| = tan(天顶角)`**。

* 正午：`|dir| ≈ 0.5`，一步走 0.4 个体素，很细。
* 清晨：`|dir| ≈ 15`，一步水平跳 **12 个体素** —— 而墙只有 2 个体素厚。

于是墙被直接跨过去了，整个房间像没有墙一样亮起来。这不是精度不够，是
**采样步长和几何厚度在同一个量级上的必然结果**，调参救不了。

现在换成 **3D-DDA（Amanatides & Woo）**：沿着光线逐个访问它真正穿过的体素，
一步不漏。它同时更快（穿过房间只要几十步，而不是 128 步盲走）和更准（墙角、
窗框、半开的门都对）。`tools/volume-probe.mjs` 用同一份 `makeInterior` 在
CPU 上复刻这条光线，所以任何「光斑去哪了」的问题都能先在这里问出答案。

#### 礼拜堂揪出的两个旧 bug（都在这一条光线上）

**一、步数上限写成了一个"感觉够用"的数字。** DDA 一步走一格，掠射光线会横穿整张
体素网格，最坏情况正好是 `dim.x + dim.y + dim.z`——礼拜堂是 226+170+60。原来的循环
上限是 `220`。跑满循环退出的光线会返回它**已经累积的透射率**，而对一条什么都还没
碰到的光线来说那就是 1.0，也就是**穿墙的满阳光**。民居小，正午太阳高、光线短，所以
这个上限一直没被碰到；礼拜堂的远侧廊有 22 格地板被"什么都没穿过"的光照亮。修法是把
上限改成从体积尺寸算出来的 `dim.x + dim.y + dim.z`，室内光照因此在低太阳时**变暗**
——变暗的那部分本来就不该存在。

**二、玻璃只会写进"已经是实心"的体素。** `buildVolume` 里那句守卫写的是
`if (data[o] !== 0) continue;`，而体积的初始填充是 255（空气）、实心是 0。于是：
窗洞中间那些本该被玻璃占据的空气格子**全部被跳过**，玻璃只在"墙已经标成实心"的
格子上生效——正好是它本该让开的地方。后果是**全项目每一扇窗都在透 100% 的白光**，
而窗玻璃标记的 `trans` 和 `tint` 从来没生效过。

它藏了这么久，是因为所有窗的 tint 都是近白色（`[1.0, 0.955, 0.86]`）：一扇透过
100% 而不是 90% 的窗，看起来就是一扇窗。礼拜堂的五色玻璃是第一个**让这个 bug 有
颜色**的东西——光穿过彩窗到达地面时，一点颜色都没有。修法是把判断反过来
（`!== 255`）。

顺带一个量纲问题：修好之后，5 cm 厚的玻璃被体素放大成两格，`trans` 和 `tint` 各乘
两次。所以 `tools/models/chapel.mjs` 里 `GLASS` 表存的是**平方根**（0.84、半强度
原色），落地时才是想要的 0.71 和满饱和色。这条没有写进引擎，因为它是资产对网格的
适配，不是网格的错。

两个 bug 修完之后，两张旧地图的变化是：**正午 1.5、日出 1.5、二层 1.3**，而同一
构建渲染两次的噪声底是 **1.2**（见 §12 的对照表）。也就是说，旧地图没有可见变化。

### 刀口：室内唯一一条没有半影的阴影边

上面这条 DDA 是**二值的** —— 体素不是空气就是实体，一条光线决定整个像素。
于是房间里每一道阴影的轮廓都是**沿着体素网格的阶梯**。这在以前看不出来，
因为室内的墙一直是半透明的：墙和墙上的窗同时解释了这个亮斑**为什么亮**和
**为什么在这儿结束**。

把近侧墙彻底隐藏之后（`cutaway = 'hide'`）就没有东西解释了。一块比周围地板
亮两档、边缘是一条直线的区域，读起来不是阴影，而是**一块躺在地板上的受光面**
—— 一块玻璃、一张垫子、一张纸。这就是「墙体上端被照射到的地方存在一个真实
的光照面」的来历：它既不是精灵图，也不是幽灵层，而是**窗光本身**。

室外的地面高度场从第一天起就带 `u_shadowSoft`，室内什么都没有。现在
`roomMarch` 沿太阳视面再取两条偏移光线（权重 0.5 / 0.25 / 0.25）：

* 全亮和全暗的点**逐位不变** —— 房间平均亮度 78.6 → 78.9，只有 4.5% 的像素
  有任何变化，且都贴在边界上；
* 光落地的**位置**一点没动，只有边缘有了宽度。窗框切出来的光斑形状照旧。

代价：室内每帧 +1.7 ms（123.3 → 125.0 ms，SwiftShader 软件光栅化）。室外
根本走不到这条分支（`u_hasRoom == 0`）。

### 半影本身又造出一个 bug：朝阳的墙面上一张「破面」的格栅

半影是 `roomMarch` 沿太阳视面取两条偏移光线，偏移量是 `u_sunSoftIndoor = 0.12`
世界单位。**而墙板厚度只有 0.14，体素是 1/14 单位**：一个站在墙上的片元，自己的
体素是实体，两条侧向偏移光线有一半概率落进**墙体外的空气**里 —— 那一路就"逃逸"、
返回全日照。三条光线的加权在体素尺度上翻来覆去（0.25 / 0.5 / 0.75），于是
**一整面平整的、被太阳照到的墙，逐像素在"全日照"和"全阴影"之间跳**，
看起来像一片细密的格栅或碎面；而拿到全日照的那些像素还要乘 `u_indoorSun = 3.0`，
于是它同时读作一圈"光晕"。这是室内版的 shadow acne，检测方法是
`--lightdebug 1`（阴影项）——墙上会出现体素周期的黑白网格，
而 `--lightdebug 22/23/24`（albedo / normal / material）三张全部是干净的，
所以它既不是贴图也不是法线。

修法是 shadow map 里的标准动作：**沿法线把光线起点抬出表面**，
`p0 = vec3(w, z) + N * (SURF_OFFSET_VOXELS / u_roomKos)`，取 2 个体素。
三条光线从此都在墙外的空气里起步、互相一致，墙面要么整片被照、要么整片在影里。
代价是标准的：表面自身投下的影子缩短约 2 个体素（0.14 单位，约三分之一格），
在窗台那种地方能看见，别处看不出来。实测：墙的阴影项均值 39.6 → 130.9（/255），
55% 的墙体像素改变，而**地板一格都没动**（±2~3 灰阶，噪声级）。

### 地板上那一排排光条：量化的是"场"，不是"边"

上面那条法线偏移修的是**墙面**。地板上还有同族的第二半，而且它在民居里一直存在，
只是没人盯着看：**被太阳照到的地板上会出现一排排平行的光条 / 暗条**，边缘硬、
宽度 5~10 像素，像贴在被照面上一层梳子。礼拜堂把它放大到了无法忽略——大面积彩窗、
浅色大理石地面、低太阳把光斑拉得很长。

这条查了三轮，前两轮我都在错误的层上找原因，写下来比结论有用：

**第一轮：以为是体积光的雾场。** `shaftAmount = 0` 一关——光条还在，于是排除。
（后来通道 7 单独打印雾场，确实能看到成片的层状结构，那是**另一个**真问题，
见下面"雾场"一节；但它不是这条光条。）

**第二轮：以为 GPU 和 CPU 反演不一致。** `volume-probe` 说那个点在阴影里，画面却是亮的。
最后发现是**我的探针写错了两次**：`game.worldAt(px, py)` 收的是 `gl_FragCoord` 像素
（**自下而上**），而我传了图像行号；修好之后又忘了镜像着色器里那个"沿法线抬 2 个体素"
的起点偏移（掠射角下 0.14 单位的高度差 = 沿墙 3 个体素）。两个都修好之后，
CPU 与 GPU 逐点吻合，包括每一级台阶。

**第三轮才找到真凶：重叠的 mark 被算了两次。** 把直射通道 1:1 打出来做二维图，
图案是这样的（`#` 暗、数字是亮度档）：

```
   ####################333###444###333###############     ← 一条条平行细光束
   ######################333###444###333#############
   ########################333###444###333###########
```

每一束宽 3 像素、间隔 3 像素，**它们是从同一扇窗出来的**——周期 0.177 世界单位。
窗户的玻璃是**一列一列**标出来的（这样窗头才能跟着尖拱走），而每列只有 0.036 单位宽，
体素是 0.071：光栅化把每列向外取整到整格，于是相邻两列**共用**一格，
而合成是按格相乘的，共用格就被收了两遍玻璃的钱 —— 一格的玻璃，一格半的玻璃，
一格的玻璃…… 于是透过窗的光被切成五六根硬边光束。

修法是把**覆盖率按种类累加，最后只合成一次**：

```
solid  covS += c            T *= 1 - covS
glass  covG += c,  tint 加权平均     T *= 1 - covG * (1 - trans)
```

mark 描述的是**一个面**，不是一个叠在另一个前面的滤镜——同一扇窗的 20 列加起来
仍然是"一层玻璃"。这一条同时解释了为什么它躲过了半影、法线偏移和更细的网格：
那些都没有碰"一格被收了几次钱"。

顺带修掉的还有玻璃本身的收费方式：原来是**每穿过一格体素付一次**，一束掠射光线
沿着玻璃走，会付三四次；现在**进入玻璃时付一次**（`inGlass` 边沿检测），
从任何角度看一扇窗的代价都一样。玻璃的 mark 也因此做成"比一格体素略厚"
（0.094 对 0.071），保证"进入"那一格一定是满覆盖的。

### 雾场：体积光自己的一层壳

礼拜堂还暴露出**空气体积**（阳光轴用的那卷雾）自身的两个问题，和上面的光条无关：

* **网格是固定格数。** `makeShaftVolume` 原来写死 `56x46x32`——格数固定、
  世界尺寸随房间变，于是民居是 0.21 单位一格，礼拜堂是 0.29。现在按固定密度
  （4.87/单位横向、9.28/单位纵向）从房间尺寸算格数：**两张旧地图拿到的还是
  56x46x32**，大房间只是格子更多，而不是格子更粗。
* **场是阶跃的。** 每格存的是"这点能不能晒到太阳"，是 0/1，而网格比房间粗 5~10 倍，
  于是空气里每一条阴影边都是 0.2~0.3 单位的硬边；光路积分过去，一束光在空气里
  站成**一排平行的板**。加一个 3x3x3 的盒式模糊（一次 19 万片元，太阳动了才跑）
  把阶跃变成两格宽的斜坡——这才是雾该做的事。模糊的是**场**，不是画面：
  模糊画面会把美术一起糊掉。

每帧成本不变（着色器循环没变），体积的构建与模糊都是一次性的。

### 只有建筑进体积

体素在室内尺度上约 3 像素，椅子腿、桌子横撑根本不存在。给一把椅子标一个
占用盒，等于在光照里盖下一个椅子大小的实心方块 —— 结果是没人认得出是什么
投出来的阴影，而且它恰好会挡住窗光落地的那条地板。

所以进体积的是 `cat === 'wall'` 的东西。家具的接地感来自它自己烘焙好的
逐像素 AO（精确到像素），阴影项则只剩一个含义：**建筑在拿阳光做什么。**
这也正是窗形光斑能读出来的原因。

## 6. 光的体积：真正的阳光轴

到这一步房间已经封住、光斑也对，但**光本身还是看不见的** —— 你看到的是一块被
照亮的地板，而不是一束穿过房间的光。真实的阳光轴不是"贴在亮处的辉光"，
它是**空气本身被照亮**：光在路上散射进你的眼睛。

所以这一版真的把这条积分算出来了。

```
① SHAFT pass（每个太阳方向重算一次，约 10 万个体素）
     对房间里每一个点跑一遍和地板用的同一条太阳光线
     → 一张 56×46×32 的「阳光可见度体积」：
        RGB = 这束光穿过来时染上的颜色，A = 这里有多亮
② 光照 pass
     沿着视线穿过这张体积积分 —— 正交等距投影让「这条视线」是一行循环：
     z 每升高一个单位，反解出的世界 xy 在两个轴上都平移 u_iso.z/(2*u_iso.y)
     → 累加出来的就是这条视线上的散射光
```

三个关键点：

* **这不是后期辉光。** 没有径向模糊、没有屏幕空间假光。光轴和地板上那块光斑
  来自**同一次 ray march** —— 决定地板亮不亮的那条光线，同时也决定了空气亮不亮。
  所以光斑和光轴永远对得上，彩色玻璃的染色也自动带进光轴里。
* **体积是粗的（1/4 分辨率），这是特性不是妥协。** 光轴本来就该是软的，
  三线性过滤免费提供了柔化；全分辨率每帧重建会比整个渲染器其他部分加起来还贵。
* **采样起点按像素抖动**，否则固定的步进会一直踩在体素网格的同一个相位上，
  在房间里留下一道道横向条纹。抖成噪声，看起来才像一张照片。

强度是 `shaftAmount`（`src/main.js`），默认 0.28：想要更戏剧化就往上推，
想要完全关掉就设 0。用 `--lightdebug 7` 可以只看这一项。

### 空气体积的边界不是房间的边界

这一项在「把近侧墙彻底隐藏」之后变成了一块**巨大、均匀、边缘笔直、洗掉纹理的
亮面**，横跨整个近侧地板。用户的描述是「这一部分的光照和空间和其他部分都不一样」
—— 说得对，因为它确实是**按室外在打光**。

房间体积的 bounds 带 0.55 的余量（墙画在图纸边缘上，会略微出挑）。阳光可见度
体积**原封不动继承了这份余量**，而在余量里 `roomVis` 的 march 一出发就在体素
网格外面，于是上报**满天阳光** —— 不管太阳在哪个方向。相机站在剖开的房间外面，
视线正是从这段余量里穿出去的，于是它把房子外面的整片天空都加到了一块太阳根本
照不到的地板上。

识破它的关键是**让太阳转**：`--lightdebug 7` 在 t=0.30 / 0.42 / 0.70 三张图上，
那条贴着两侧墙的 V 形亮带**一动不动**。光会跟着太阳走，几何不会。

修法是让空气体积只覆盖**建筑本身**（`cat === 'wall'` 那批 mark 的包围盒），
体积之外散射为零。这一步同时是位置的平滑函数 —— 这和「逐像素拿墙的体积遮挡去
截断 march」是两回事：后者会在一个墙根本没画出来的剖切视图里，沿着窗洞打出一
条条丝带（试过，见 §12 的排查表）。

上线后：近侧地板这一项从 147/113/98 掉到 83/56/48（房间中段仍是 1.4，未受影响），
白天室内平均亮度 69.0 → 66.0，夜里 40.5 → 39.5。

### 黄金时刻的「另一块地板」：真凶是**光从被隐藏的那两面墙进来**

上面那条修完之后，16:03 的帧正常了。但 **22:58（GOLDEN HOUR）仍然**有一片平坦的
暖色地板铺在近侧，看起来像另一个空间。

**先说结论，因为这一节的旧版本给错了结论。** 旧版本量了下面这张表，只看"总亮度"
一列（近侧带 52.5 对房间中段 51.7），于是写下"**那里没有多出来的光，也没有多出来的
面**……这一半不是渲染错误，是**构图**"。这个结论是错的，而且它让排查停了很久。

破法不需要新理论，只需要把"隐藏"这件事真的做一次减法：**把 `+x`/`+y` 两面墙的窗洞
在光照体积里封死**（`winFront/archFront/winRight/archRight` 清空，画面一个像素不改），
同一时刻同一机位再量一次地板（`work/dsh-tiles.mjs --time 0.72`，每格中央亮度）：

| 地板行 | 设计如此 | 两墙窗洞封死后 |
| --- | --- | --- |
| 近侧带 j=7 | 57 81 84 50 71 47 53 85 94 82 39 | 41 39 41 41 42 41 42 41 39 41 26 |
| 近侧带 j=8 | 50 63 75 62 51 49 52 65 78 76 63 | 43 42 41 44 43 44 44 45 42 44 41 |
| 房间中段 j=4 | 31 47 67 59 67 59 72 61 67 88 39 | 29 16 39 53 50 22 24 36 36 34 26 |

近侧带整条塌到 ~41–45 的纯环境光地板。也就是说：**那条带子的亮度全部是从被隐藏的
那两面墙的窗洞进来的**——不是"没有多出来的光"，而是"多出来的光全部有一个现在看不到
的来源"。同理，房间中段也塌了一截，因为低太阳是斜着从近侧墙灌进来的。

把这件事说穿，就回到室内布光的一个结构性事实（§4 / `src/interior.js` 的采光口分配）：
**这间房白天所有的光都从相机侧那两面墙进来**，因为 `sunAzimuth()` 的方位角整天都在
`+x/+y` 一侧，而落地窗（`wall_window_tall`）也刻意给了这两面墙。所以：

> 隐藏近侧墙 = 同时删掉房间里**每一个光子的可见来源**，并把它原本挡住的那条地板露出来。

近侧带和房间中段的"氛围不一样"因此是必然的，它是一个**美术结构问题**（光源长在会被
剖掉的墙上），不是着色器算错。可选的解法见 §13。

那张旧表的另一处问题也记在这里，免得后来人再被它误导：**四列不是同一把尺子。**
"总亮度"是取样块的平均值，而"直射"那一列的 168.8 是在一块**光斑**上取的单个像素——
直射比同一个取样点的总亮度还大，说明这一行是混着两个位置量出来的，因此
"两边总亮度一样"这个比较本身就不成立。（同一张表里还有一处相反的线索被忽略了：
空气散射近侧带 21.3 对房间中段 1.3，差 16 倍——那正是"多出来的光"。）

可以调的旋钮是 `game.shaftAmount`（空气里那束光的强度）。默认在 `ghost` 下 0.28、
`hide`/`off` 下 0.18；设 0 就完全关掉光轴。**它治不了这块地板**，但能改变它有多"发亮"；
而且这个"默认跟着剖切走"本身就是 §1 说的那个不变量破洞。

## 7. 阴影：为什么室外根本没有影子

先是一个**一行的 bug**，它让室外的阴影从未存在过。

运行时的阴影靠一张俯视高度场：离线阶段为每个模型烘一张「从上往下看的高度戳」，
运行时按摆放位置盖进 1280×1280 的场里。盖戳的循环是这样写的：

```js
const [sx, sy, sw, sh] = sp.s;      // ← 印在 ATLAS 里的位置
...
const si = (y * sw + x) * 4;        // ← 却按 sprite 局部坐标去索引整张图集
```

`sp.s` 是**图集坐标**，`sp.sx / sp.sy` 才是**世界偏移**。读的时候用了后者算位置、
却用前者当索引，于是**每一个模型都去读图集左上角那一块**。高度场整张是空的，
室外一栋房子、一棵树都不投影。

修好之后（`buildHeightmap` 现在显式区分这两个坐标系），室外的影子第一次出现：
长凳、树、屋顶、走动的人全都在地上。

### 近处细、远处按几何级数增长 —— **已经被最大金字塔取代**

高度场步进原来用**均匀步长**（0.075~0.125 世界单位）。步长要够粗才能跨过整张地图，
但这么粗的步长**分辨不了近场**——而阴影的形状、与地面的接触、每一个小物体的轮廓，
全都发生在近场。结果就是细而薄的几何碎成斑点。

```glsl
float st = u_shadowStep * 0.38;
for (int s = 1; s <= 40; s++) {
  tt += st;
  st = min(st * 1.135, u_shadowStep * 5.0);   // 起点约 0.03 单位，逐步放大
  ...
}
```

近场分辨率提高约 3 倍（0.03 单位 ≈ 1 像素），远处仍然能覆盖 35 个单位。
**但这条思路本身有天花板，而且后来真的撞上了**：见下一节。

### 低太阳下阴影碎成一片小圆点：从「猜步长」改成「证明能通过」

上面那个几何级数步长是**采样**，不是**证明**：比步长更薄的遮挡物，只要没有一次采样
正好落进去，它就完全不投影。而这个 march 的参数化是**每步升高 1 个高度单位**，
所以每步在地面上跨过的距离是 `|sunDir.xy / sunDir.z|`：

| 时刻 | `dz` | 地面步距 | 栅栏柱/树干的截面 |
| --- | --- | --- | --- |
| 正午 | 0.9 | ≈ 3.6 texel | 1–3 texel |
| 黄昏 | 0.03 | **≈ 20 格 = 411 texel** | 1–3 texel |

黄昏时一根两 texel 宽的柱子每 400 texel 才被采到一次，**影子只在恰好命中的地方出现**；
而 `pen = max(pen, th - h)` 是布尔的（擦顶→0，穿心→接近满值，中间没有过渡），
再加上做半影的**五点十字核**（`e = shadowSoft * 0.45`，黄昏时 e ≈ 16 texel），
每一次稀有的命中被膨胀成一个直径 32 texel（1.6 格）的圆盘 —— 这就是"影子变成
一个个快速移动的小圆点、散开了"的全部机制。调 `shadowSoft` 治不了它，因为**漏掉是布尔事件**。

现在室外相位走的是**最大金字塔（maximum mipmap / hi-Z）保守行进**：

```
level L 的每个 texel = 下一级 2x2 的最大高度
h > hm(level L)  ⇒  这条射线可以证明它穿过了该块里的一切  ⇒  按间隙前进
被挡  ⇒  降一级继续看；降到 level 0 还被挡  ⇒  真的有东西
```

* **没有步长这个参数了**：一次迭代要么证明通过、要么降级细看，两 texel 宽的柱子
  在构造上不可能被跳过；
* 迭代次数**下降**（通过就升粗，跨过远场只要几次），实测 640×360 单帧
  SwiftShader 从 140 ms 降到 **102 ms**；
* 半影改成**匹配足迹**：被挡时按距离读一次 `textureLod`，取太阳视直径覆盖的那块
  高度（PCSS 的思路，一次采样替代原来的五次），低太阳下不再膨胀成盘；
* 越过首个遮挡后**继续走 8 个 texel 取最深穿透**——否则擦到谷仓一角会被当成
  "穿透≈0"，在 1.5 单位的半影下把整片阴影冲淡；
* 结果是 `u_sunDir` 的**纯函数**，同一角度必定同一张图（QA 逐像素比对安全）。

A/B 开关：`game.shadowMarch = false` 回到旧的几何级数步进，同一帧可以直接做差。
两者的阴影面积差（黄昏 47–61%、正午 16%）**正好等于十字核的膨胀半径**——
也就是说旧路径多出来的那部分不是阴影，是它自己糊出去的。

金字塔本身由 `buildMaxMip()` 建、`updateMaxMip(rect)` 局部维护（村民每帧动一下就重建
2.2 M texel 是荒谬的），`HEIGHTMAX_FS` 逐级做 2x2 取最大。两个坑值得记下来：
`generateMipmap` 是**平均**，这里的算子必须是**最大**；以及往金字塔的某一级渲染时
**不能同时采样这张纹理**（哪怕采的是另一级）——WebGL 不会报错，它返回 0，
于是金字塔是空的、每一束光都"证明"自己畅通、室外**完全没有影子**。

角色则完全换掉了思路。原来给它盖的是一个**又高又窄的圆顶**（半径 0.30、高 1.05）——
低角度太阳下它会被拖成一条散开的糊影。一个 27 像素高的小人不应该有一个"写实"的
投影高度戳；现在用**又宽又扁的接触暗斑**（半径 0.40、高 0.30）。
室内也用同一套：房间另外拿一张**只有动态戳记的空高度场**，所以村民在屋里
也有脚下的接地暗部 —— 而建筑本体仍然只由体素体积负责。

## 8. 渲染管线

```
离线（Node，零依赖）                        运行时（浏览器，WebGL2，640×360）
─────────────────────────                   ────────────────────────────────
程序化建模（几何 + 世界空间图案）              ⓪ 焦点深度图（1/2 分辨率 RGBA8）
  → 逐顶点 AO 光线烘焙                            把「相机必须看见的东西」画成
  → 软件光栅化（超采样）                          世界空间盒子，深度测试留下
  → 解析出四路 AOV：                              每个像素上最近的那个表面
      albedo  无光照材质色                     ① G-buffer pass
      nrm     着色法线 + 表面高度（→ 深度）         不透明世界 = 一次 instanced draw
      mat     AO | 高光 | 自发光 | 面组 ID          **写 gl_FragDepth**，24 位深度
      stamp   俯视高度戳（世界空间）                MRT 输出：
  → RGBA8 PNG 图集（不做色板量化）                   RT0  albedo + alpha
  → 体积标记（solidBox / glassBox）                  RT1  世界法线 + 表面标记
                                                    RT2  AO / 高光 / 自发光 / 高度
                                              ①b ghost pass（同一份精灵、同一个投影）
                                                  **与①共用同一个深度缓冲**，
                                                  逐像素与⓪比较决定哪些像素淡出
  → RGBA8 PNG 图集（不做色板量化）           ①c 阳光可见度体积（56×46×32，室内）
  → 体积标记（solidBox / glassBox）              太阳一动就重跑一遍房间里的光线，
                                                记下"哪里的空气是被照亮的"
                                             ② 世界高度场（1280×1280）
                                                静态建筑按戳记写入，
                                                角色每帧用 texSubImage2D 盖章
                                             ③ 光照 pass（全屏）
                                                两层各自从 (屏幕坐标, 高度) 反解
                                                世界坐标、各自着色、按 alpha 合成，
                                                并沿视线在①c 里积分出空气散射
                                                ——正交等距投影使这几步都是精确的，
                                                所以不需要世界坐标缓冲
                                             ④ 泛光（1/4 分辨率亮部 + 双向模糊）
                                             ⑤ 后处理：色调映射 / 分级 / 暗角 / 颗粒
```

### 六个关键设计

**① 世界坐标是反解出来的，不是存出来的 —— 深度也是。**
投影是正交等距的，`screen = f(x, y, z)` 可逆：给定屏幕像素和该像素的表面高度
（存在 RT2 的 alpha 里），`(x, y)` 就是唯一的。省下一整个 render target，
而且比 8 位世界 XY 精确得多。**深度同样白送**：`dep = (x+y) + (2·HH/ZPX)·z`，
其中 `x+y` 直接落在投影里，连 x、y 都不必解出。所以那个 24 位深度缓冲没有增加
任何一个资源，它只是把已经有的数据用起来（见第 2 节）。

**ghost 图层复用了这一点**：一面被透明化的墙用它自己的高度反解出自己的世界坐标，
所以它被照亮的方式和它挡住光的方式是同一个坐标，不会出现「影子在这里、墙面在那里」。
幽灵图层与不透明图层**共用同一个深度缓冲**，所以一面被透明化的墙仍然会输给真正
站在它前面的东西 —— 剖切不会在门口那个村民身上穿个洞。

**② 图案梯度 → 细节法线。**
这是让预渲染精灵在实时光照下不"塌成塑料"的那一步。
每种材质带一个世界空间程序化图案（木板缝、砖缝、瓦垄、犁沟、茅草、叶簇……），
光栅化时用有限差分求该图案的梯度并扰动法线：

```
n' = normalize(n − ∇h · k)      h = patternHeight(x, y, z)
```

没有这一步，一面木墙的法线是常数，灯笼扫过去只是一块死板的渐变；
有了它，砖缝、板缝、犁沟在灯下真的"有厚度"。
响应是饱和的（硬边图案的原始梯度是软边图案的上百倍），
所以 `bump` 强度直接等于最大切向倾角比 —— `0.75` 就是"最多偏 37°"。
**这一整套不需要任何额外贴图，改几十行代码即可。**

**③ 大尺度变化必须在世界空间里连续。**
一开始草皮用了 4 个亮度不同的瓦片变体，结果整片草地是一张棋盘格。
正确的做法是：所有草地变体共用**同一个材质**，色调变化来自图案里一个
几个瓦片宽、**跨瓦片连续**的世界空间场 `patch()`。于是草地是一片草甸，
而不是一千张贴图。

**④ 屋内屋外同一个曝光模型，两种曝光值。** 现实里室内比室外暗两三个数量级，
眼睛会自己适应；固定曝光的渲染器不会，所以进屋时曝光乘 1.5。镜头的
「适应」是这套管线里唯一一处非物理的手动挡。

**⑤ 正交等距投影让"沿视线积分"变成一行循环。** 体积光通常要靠屏幕空间模糊或
再投影来近似，因为重建一条世界空间视线很贵。这里不用：固定屏幕像素 + 变化的 z
对应的世界坐标是**线性**的（z 每升一单位，xy 同时平移 `ZPX/(2·HH)`），
所以穿过体积的视线就是一次加法循环。第 6 节那套阳光轴的成本几乎全在
"重建可见度体积"上，而不在每条视线上。

**⑥ 焦点图的空像素清成远端，不清成 0。** 一句话的取舍，但错了就全错：
这张图用线性过滤采样来柔化幽灵边界，而 0 在深度里是「极远」。清成 0 会让边界
那一圈混出**更小**的深度，于是焦点盒子**外面**比盒子**里面**更急于透明。
清成远端之后，混合只可能更保守 —— 而「保守」在这里的含义是「宁可少淡一点」。

## 11. 玩法与操作

M0 是**光影垂直切片**：地图编辑与生产经营都还没有，重点是把"这个风格成不成立"验证掉。

| 按键 | 作用 |
| --- | --- |
| `1`–`8` | 跳到清晨 / 正午 / 黄昏 / 日落 / 夜晚 / 雾晨 / 上午 / 午后 |
| `[` `]` | 微调时刻 |
| `Z` | 缩放档位（WIDE 640×360 → MID 480×270 → CLOSE 320×180） |
| `E` | 进屋 / 出屋 |
| `U` / `PageUp` `PageDown` | 上下楼（在屋外按等于进屋；一层 ⇄ 二层） |
| `Space` | 暂停 |
| `+` `-` | 时间流速 ×0.25 … ×8 |
| `R` / `F` | 雨 / 雾（会实时改变光照、色温、环境光与雾浓度） |
| `K` | 剖切模式：淡出 → **整个移走** → 画实（见第 1 节） |
| `L` `N` `M` `J` | 按类别隐藏 灯 / 窗 / 窗帘 / 挂件 |
| `WASD` / 方向键 / 拖拽 | 平移相机 |
| 滚轮 | 直接刷时间 |
| `H` `G` | 帮助 / 调试面板 |

场景里的一切**都是活的**：五个村民，其中一个在屋里走动、锄地、浇水；
灯笼和篝火在入夜时亮起并微微闪烁；温室里的补光灯整夜透出橙色。
角色会被真实光照照亮，也会在地上投下真实的太阳阴影 —— 室外靠高度场，
室内靠动态戳记。

**看室内的正确姿势**：按 `E` 进屋，然后按 `[` `]` 或滚轮刷时间。近侧的两面墙会
为你淡成 24% 的幽灵、只留一条轮廓线，房间整个可见；看那道光斑怎么从东墙爬到
地板上，以及**空气里那束光本身**。早晨 `1`、上午 `7`、正午 `2`、午后 `8`、
黄昏 `3` 是光斑差别最大的时刻 —— 正午的太阳高，光斑贴着墙；清晨和黄昏它会把
光带甩到房间中间。

**看遮挡的正确姿势**：在室外把鼠标移到房子后面的地块上（或者等某个村民绕到
谷仓后面）—— 挡住它的**那一小块**建筑会淡下去，而不是整栋。屋顶上会出现一个
和村民一样大的窗口，其余部分照样是实心的。

```bash
                                                  # 图集重打包后，旧精灵是否逐像素不变
node work/dsh-zoom.mjs shot.png out.png 336 220 84 46 8
                                                  # 整数倍最近邻放大（数格子用，不插值）
node work/dsh-line.mjs --t 0.33 --debug 15 --row 236 --x0 348 --x1 392

```

**加一张新地图之后，先量"旧地图有没有变"，再谈新地图。** 这一轮加礼拜堂时同时改了
三处引擎代码（玻璃守卫、DDA 步数上限、相机夹取），所以回归是三道独立的测量，而不是
一句"应该没事"：

* **像素**：图集是货架打包的，加模型会把每个精灵矩形重排。`work/dsh-sprite-diff.mjs`
  按精灵 id 解开两边的四张 AOV 图，逐通道比对矩形**里面**的像素——261 个旧精灵全部
  逐像素相同（"矩形搬家了"是允许的，"像素变了"才是回归）。
* **图纸**：`check-interior` 对三层各跑一遍，对象数、体积标记数、可走格 / 走不到的
  清单逐项对照基线。一层 84/219 + 6 格走不到，二层 67/164 + 全通，与加礼拜堂之前
  **逐字相同**。
* **画面**：`work/dsh-chapel-shot.mjs --root work/baseline-m7` 直接拿备份目录当站点
  根渲染旧代码，与当前源码同机位同时间对比（`work/dsh-align.mjs`）。正午 1.5、
  日出 1.5、二层 1.3；同一构建渲染两次是 1.2。

新增的两条图纸检查也值得记一笔，因为它们都是"平面图看不出来"的东西：
`check-interior` 现在会把每件家具的**烘焙包围盒**两两求交（不是按格子数重叠——列柱
站在两格之间，"共享格子"是正常的，"共享空间"才是 bug），并且会拿摆好的墙件高度去
核对天花板盖在哪一层（`CHAPEL_H === CH`，差 0.02 就报错）。

**调试图层**是这套管线最重要的工具：`--debug 1..4` 直接把 G-buffer 的每一路
画到屏幕上，`--lightdebug` 把光照的每一项单独画出来。这一版的三个 bug 都是靠它
定位的：室外阴影完全不出现（高度场是空的）、正午室内整片黑（体素采样值域搞错）、
巨大的一块半透明幽灵（ghost 图层空帧没清）。

升级到深度缓冲的过程中又多了三个，也都是靠调试图层定位的：

* **焦点深度被夹在 0**（`--lightdebug 9` 一眼可见）：深度是 `x + y + K·z`，在地图
  近角之外是负数，编码时夹到 0 就读成「这里没有焦点」。修法是编码前加原点。
* **焦点用的是地板而不是房间体积**（同上）：后墙就立在自己的地板上，于是整个背板
  化掉。后来这个方案被整个换掉了——见下一条。
* **一次静默的彻底失败**：焦点图没生成时，室内每一面 `cut` 的墙都变成实体，把它
  后面的家具全吞掉，控制台里什么都没有。这是最坏的一种 bug，因为它看起来像
  「渲染管线写坏了」。修法是把室内的剖切改成**声明式**的，并给着色器加兜底分支
  和一条控制台警告（见第 1 节）。`tools/probe-stale.mjs` 专门守这条路径。

另外加了一道**语法门禁**：`shaders.js` 里装着 GLSL 模板字符串，注释里一个反引号
就会提前结束字符串，而症状只是「BOOT FAILED」外加一个不认识的标识符。`verify.mjs`
现在先用 `node --check` 把 `src/` 全部过一遍再启动浏览器，报出文件和行号。
（这一轮又踩了一次，门禁当场报出行号。）

**「这一像素上是什么」不要靠猜**：`game.pick(px, py)` 返回上一帧提交的、屏幕
矩形盖住这个点的所有精灵图——图层、alpha、高度区间、绘制顺序、id。`tools/pick.mjs`
是它的命令行外壳。这一轮的结论（房间中部那块亮面**不是**任何精灵图，就是地板）
就是它给的：在那个位置，除了 `id: ''` 的地板条和 `furn_table`，什么都没有。

**量"世界坐标"要小心两套像素约定。** `game.worldAt(px, py)` 收的是 `gl_FragCoord`
的像素（**自下而上**），而截图/画布像素是自上而下的。把图像行号直接传进去不会报错，
它会安静地返回**镜像那一行**的世界坐标——这一轮就是它让我一度以为"GPU 和 CPU 反演
不一致"。凡是把屏幕像素和世界量对起来的探针，都先在注释里写清用的是哪一套
（`work/dsh-line.mjs` 现在就是照这个写的）。

**`work/diag/frametime.mjs <indoor|outdoor> [半影宽度]`** 用同一套方法量帧时间，
最后一个参数直接改 `renderer.light.sunSoftIndoor`，所以「加了这个功能贵多少」
是一个可以复现的数字，不是估计。

### 一次「被隐藏功能揭发」的旧 bug

近侧墙能彻底隐藏之后，房间中央出现了一块边缘笔直、比周围亮两档的地板。
排查顺序和每一环的结论：

| 假设 | 怎么否掉的 |
| --- | --- |
| 幽灵层没清干净 | `--lightdebug 6` 全黑，ghost 层是空的 |
| 阳光轴的体积边界 | `--lightdebug 7` 一开始看错了 —— 见下 |
| 某块精灵图残留 | `game.pick` 只返回地板条和桌子 |
| 室外环境光串进了室内（`insideRoom` 假） | `--lightdebug 2` 在这个区域是白的 |
| 是太阳直射 | `--lightdebug 1` 在这儿只有 1–26/255 |
| 就是太阳光斑本身 | 正午和夜里各渲一张：**夜里没有，正午更亮** —— 它跟着天空走 |

这一步只走到「它跟着天空走」，于是我在 **`roomVis` 的 march 上加了半影**（见第 5 节），
治好了刀口，**但没治好像素**。用户第二次指出问题后，逐项拆分光照才发现真凶：

| 项 | 近侧地板 | 房间中段 | 结论 |
| --- | --- | --- | --- |
| 太阳直射（ldbg 1） | 1.4 | 1.4 | 都不是直射 |
| 点光 / 窗洞（ldbg 4） | 28–118 | 8–16 | 近窗本来就该亮 |
| **阳光轴散射（ldbg 7）** | **147 / 114 / 98** | **1.4** | **差 100 倍，就是它** |

再往下：CPU 复刻（`tools/volume-probe.mjs --t 0.419`）明确说地板只有 2/99 格见得到
太阳，那张图整片是 `#`。**地板是暗的，地板上面的空气却是亮的 —— 两者矛盾，所以
一定是体积错了。** 最后靠「让太阳转」定性：亮带不随太阳移动，是几何不是光。

两次绕路值得记下来：

* **只加半影**：边缘从 1 像素跳 65 变成 8 像素斜坡，房间均值 78.6 → 78.9，
  成本 +1.7 ms —— 是个正确的改进，但**不是这次问题的解**；
* **逐像素用房间体积截断 march**：在一个近侧墙被隐藏的视图里，视线穿过的是**体积
  里仍然实心的墙**，于是绝大多数像素立刻截断，只有穿过窗洞玻璃的活下来 ——
  房间中央出现四条竖直的「丝带」，正好是窗洞的形状。已回退。

**可复现截图**：场景生成完全确定（固定种子），截图前会 `paused = true` 并钉住时刻，
所以 `work/shots/` 里的对照图跨运行可比 —— 但**不是逐位相同**：同一帧跑两次的差异是
约 1.3 灰阶（来自后处理的颗粒动画与灯光的 `flicker`，两者都跟 `clockT` 走）。做逐像素
断言时把这个数当噪声底，别把 1–2 灰阶的差当成回归。

### 另一类陷阱：单文件构建和 dev server **不是同一份语义**

`dist/homestead98.html` 是把 11 个模块塞进一个 `<script>` 的注册表里（`build-single.mjs`），
每个 importer 变成解构赋值。真实 ESM 的 `import` 是**实时绑定**，解构是**取值快照**——
于是任何 `export let` 都会在单文件里永久停在初始值，而 dev server 一切正常。

踩到的版本：`iso.js` 用 `export let HW/HH/ZPX`，`setProjection(1.5)` 进屋时原地改写它们。
单文件里 `main.js` 手里永远是户外的 16/8/22，**着色器反投影把每个像素算到 1.5 倍远**，
室内透射率体积采样错位 → 阳光灌进房间、室内遮罩缩成一小块，而且**只在双击那个 HTML 时出现**。
症状极具误导性：dev 正常、截图正常，用户看到的却像"另一个房间"。

现在有两道构建期门禁，都不会再让它静默溜过去：

* 任何模块出现 `export let/var`（可变导出 = 实时绑定）→ 构建**直接失败**，并把文件与行号
  打出来，要求改成"导出一个可变对象、用时读字段"（`src/iso.js` 的 `ISO` 就是范例）；
* 任何 `import` 解析到的文件不在 `MODULES` 清单里 → 构建**直接失败**（这是加二层时踩的
  第二次：清单漏了新模块，单文件白屏，控制台里只有一句 `missing module`）。

**改完 `src/` 一定要重新 `node tools/build-single.mjs`，然后 Ctrl+Shift+R。** 想知道
眼前这个页面是哪一份：启动日志里每个楼层会各打一行体积尺寸（`indoor:` / `upstairs:`），
而 `game.STOREYS`、`game.UP` 只有当前源码才有。

## 13. 已知取舍

* **"剖切只动相机、不动光"这条不变量现在是被破坏的，破坏它的是 `src/main.js` 里
  `shaftAmount` 那一行**（`ghost` 0.28 / `hide`·`off` 0.18，见 §1）。这是全工程唯一
  一处"隐藏墙壁真的改了光照"的地方，也是 §6 那块"另一块地板"排查被绕进去的一部分原因：
  做 A/B 时两张图的光照本来就不同。**修法是一行**（`?? 0.28` 一个常数，其余交给
  `game.shaftAmount` 这个显式旋钮）。没直接改掉是因为它同时是美术手感旋钮，值应该由
  你定；改完请把 §1 与 §6 的这两段一起更新。
* **室内白天的光全部从相机侧那两面墙进来**（§4 的采光口分配 + `sunAzimuth()` 的偏置）。
  于是"隐藏近侧墙"必然删掉房间里所有光子的可见来源，露出来的近侧带必然比别处亮
  （黄金时刻实测：封死那两面墙的窗洞后，近侧带从 50–94 掉到 41–45 的纯环境光）。
  三个方向可选：① 保留 24% 幽灵（现状默认，光斑有解释）；② `hide` 时让窗/门零件以
  低 alpha 留下，即"墙没了、洞还在"；③ 把落地窗换到背景那两面墙、并把太阳方位角偏置
  翻过去（治本，但会改动室外光照方向）。
* **一个体积对应一栋房子**。M2 只给一栋建筑建了体素体积，相机进入它时体积才启用。
  多栋房子轮流进入需要多卷体积（着色器里加一层循环即可），目前没做。
  （同一栋房子的**两层**各自有一卷，那是已经做了的：见第 3 节。）
* **礼拜堂比视口大**，所以相机永远无法一次装下它：15×11 的地板在 WIDE 分辨率下
  横竖都比 640×360 大。默认机位取 `(7.5, 4.5)`——地板全在画面内、后墙顶端刚好
  切掉一点——剩下的靠平移。相机的夹取范围改成了"房间越大、可平移越多"
  （`2 + max(0, w-11)*0.5`，民居因此**一格都没变**），但这是缓解，不是解决：
  真正要一次看全，得给大房间单独一档更宽的 `ZOOMS` 分辨率。
* **柱列的列间距决定了走道宽度**。中殿 5 格 = 2 格长椅 + 1 格中走道 + 2 格长椅，
  正好铺满，于是长椅两端离柱列线只剩半格，两侧廊只能从**尽端的横向走道**进出。
  第一版图纸没有留这条横向走道，`check-interior` 报出 84 格可走里 62 格走不到——
  平面图看不出来的东西，洪水填充一眼就看出来了。
* **玻璃的 `trans`/`tint` 数字是"网格平方根"**（见第 5 节）。它们同时是亮度：
  穿过两格玻璃实际透射约 0.71。要更亮就把整张 `GLASS` 表往上抬，但它会和
  "彩窗本来就不该透那么多光"冲突。
* **一层没有楼梯口**。二层有楼梯洞（(3,4)-(4,4) 两格没有地板，配矮墙栏杆与石板边），
  但一层的图纸刻意没动——「加二层不要重做一层」是硬要求。所以从楼下看不到那段楼梯；
  要补的话是在一层找一个格子挖洞 + 加栏杆，属于改一层图纸，需要单独确认。
  真正要一段能看的楼梯还需要一个新的 `furn_stairs` 模型（重新烘焙图集），
  目前用的是「洞 + 栏杆 + 提灯」这套不依赖新素材的表达。礼拜堂的圣坛没有垫高也是
  同一个原因：室内的地面高度是平的，抬高一块地板会让地板精灵和内墙对不上，
  所以圣坛的台基做在模型里（`furn_altar` 自带座），而不是做在地图里。
* **体素分辨率是 14/格 · 11/单位**，所以任何几何细节的尺度下限就是 1/14 世界单位
  （屏幕上沿光线横向约 1.7 px）。体积场现在存的是**覆盖率**，所以阴影边与玻璃边界是
  连续的坡度而不是体素台阶（见第 5 节末）；但**比体素更细的结构仍然是靠覆盖率近似出来的**，
  一片 5 cm 厚的玻璃在体积里就是一格左右的半透明面，窗棂（7.5 cm）也只有一格宽。
  再往下要真实，就得抬体积分辨率，那是一次内存 ×8 的交换。
* **阳光轴是"单次散射"**：只算了太阳 → 空气 → 眼睛这一条路径，没有多次散射，
  也没有参与介质沿高度变化的密度模型（只有一个线性衰减）。所以它读起来是
  "空气里有光"，不是"尘埃在飞"。
* **阳光可见度体积在太阳移动时每 3 帧重建一次**：静止时零成本，快进时间时
  会有一点代价（约 10 万个体素 × 一条光线）。这是个明确的取舍，不是遗漏。
* **深度是算出来的，所以它的精度等于高度通道的精度**。`nrm.a` 是 8 位、
  按精灵自己的 [z0,z1] 归一化：一面 2.2 单位高的墙大约 0.009 单位一步，
  折算成屏幕不到 0.05 像素。对这个尺度绰绰有余，但如果以后要做
  真正的斜坡地形（一个精灵里几十个单位的高度跨度），这里会先不够用。
* **写 `gl_FragDepth` 会关掉 early-Z**，精灵 pass 的每个片元都要进着色器。
  在 640×360、一千多个 quad 的规模上测不出来（比升级前的画家排序还略快，
  因为遮挡关系不再依赖绘制顺序），但这不是一个可以无限堆量的结构。
* **ghost 图层仍然只有一层**。两个都被透明化的遮挡物如果在屏幕上重叠，
  靠后的那个会被覆盖 —— 不过现在**谁近谁赢是确定的**（共用深度缓冲 +
  深度写入），不再取决于绘制顺序。
* **焦点是盒子，不是村民的轮廓**。所以屋顶上开出来的是一个「村民占的那几格」
  大小的窗口，而不是逐像素的人形。窗口比人略大是有意的：宁可多露出一圈地面，
  也不要因为差两像素而让人被切掉一角。
* **`rot` 与 `rots` 很容易踩坑**：`rots > 1` 的模型在 manifest 里存的是 `id#0..id#3`，
  没有裸 `id`。查 `atlas.get('furn_table')` 会静默返回 undefined。
* **点光源不投影**（只有太阳投影）。夜里灯笼照到墙的另一侧不会变暗。
  室内的门户光源同理，所以窗口的补光会穿过内墙 —— 单间房看不出来，多间房就会。
* **没有光线弹射**：室内补光靠门户光源与一个偏暖的平坦环境项近似，不是真正的 GI。
* **进屋时曝光 ×1.5** 是手动挡，不是自动适应。
* **还没有阳台／凸窗**：落地窗已经把"更大的开口"这条路走到了，再往前需要
  室外平台 + 栏杆 + 房间外面的一点世界（目前房间之外是虚空）。
* **屋顶只有 8×6 一种尺寸**。屋顶是一个整体网格（山墙两端必须收口，
  分片会让瓦片图案每格重复），所以换房型要加一个 `makeRoof(id, w, d)`。
* **雨只有色彩分级**，还没有雨丝粒子与地面涟漪。
* 地形仍然是平的：没有真正的高度场起伏，悬崖、台地、地窖都还没有。

## 14. 怎么加内容

加一栋建筑：在 `tools/models/buildings.mjs` 里追加一个描述符 ——

```js
{
  id: 'bld_watermill', name: 'WATERMILL', cat: 'build', fp: [3, 4], seed: 401, cap: 4.2,
  build(b) {
    // b 是 Builder(3, 4, 401)：x/y 以格为单位，z 以世界单位（1 单位 = 22 px 高）
    const f = cottageBody(b, 3, 4, 2.0, { wall: 'woodPlank', frame: 'beam' });
    opening(b, 'x+', f.xf, 2.0, 1.2, 0.6, 0.6, { glass: 'glass' });
    gableRoof(b, 3, 4, 2.0, 1.0, { mat: 'roofTile' });
  },
}
```

然后 `npm run build`。想让它在夜里发光，用 `glassLit` / `lampGlass`；
想让它亮起来照亮周围，在 `src/world.js` 的 `LIGHT_RULES` 里加一条按 id 匹配的规则。

**它会不会挡镜头**由 `cat` 决定：`build` / `wall` / `roof` 默认允许为相机让路，
其它类别默认不允许。单独一件想允许（或不允许），在描述符里写
`cut: true` / `cut: false` 覆盖。

注意 `cut` 只是一个**许可**。室内的「必须让路」是场景在 `place(..., { cut: 1 })`
里说的（房间的四条墙边就在 `CAM_SIDE` 那一行），室外的许可则要等焦点里真的有人。
一件 `cut` 的东西默认完全不透明。

想让它出现在隐藏开关里，在 `tools/build-assets.mjs` 的 `ROLE_BY_ID` 加一条正则，
它就自动进 `game.hide`；匹配不到任何一条的模型 role 为 `null`，永远不会被藏掉。

加一种材质：在 `tools/lib/materials.mjs` 追加 `[name, hex, pattern, specular, emissive, bump]`，
`pattern` 取自 `tools/lib/patterns.mjs` 的 `PAT`，`bump` 是凹凸强度（0 = 光滑）。

加一间室内：写一个新的 `makeXxxInterior(atlas)`，返回同样形状的
`{ w, h, ground, objects, marks, door, bounds }`，用 `place()` 摆家具、
`wall()` 挂墙件、用 `b.solidBox/glassBox` 的标记去描述**建筑**（家具不要标）。
然后 `node tools/check-interior.mjs` 会把这份图纸体检一遍。

礼拜堂是这条路径的第三次走通，完整清单只有五项（`src/interior_chapel.js` 是第 1 项）：

1. `roomKit(atlas, {w, h, seed})` + `finishRoom(kit, {door, wallH})` —— 房间的骨架
   和天花板。`wallH` 只有一种情况要写：墙不是 2.2 高（礼拜堂写 4.2，并且必须等于
   `tools/models/chapel.mjs` 里的 `CH`，`check-interior` 会核对）。
2. 新模型写进 `tools/models/<kit>.mjs`，用一种类别（`wall`/`floor`/`furn`），
   墙件守 `+y` 边约定，然后 `node tools/build-assets.mjs --set interior`。
3. `src/main.js`：`makeXxxInterior` → `prepare(...)` → 放进 `flats[]`、`SCENES`、
   `STOREYS`，各一行。`enter()` 会把投影、图集、高度场、体积、相机全换好。
4. `tools/check-interior.mjs` 与 `tools/volume-probe.mjs` 的 `--storey` 表里加一项。
5. `src/ui.js` 的 `NAMES` 加一个显示名。

**墙件进体积这件事决定了房间怎么被照亮**：一扇窗不是一个装饰，它是这个密封盒子上
唯一的洞，洞的位置和大小决定光斑落在哪、能走多远（`throw = 洞的高度 / tan(太阳高度角)`）。
`b.glassBox(..., {trans, tint})` 里的 `tint` 是**逐体素的透射颜色**，五色玻璃因此
不需要任何新着色器。想确认某一刻地板收到的是什么颜色，用
`node tools/volume-probe.mjs --storey <名字> --tint --t <时刻>`。

家具的叠放**不需要声明**：深度缓冲会自己解决。只有两种情况下你才要写点什么 ——

```js
under(rug_round, 4, 4);              // 恰好平铺在地板上：只用来定平局
over(oil_lamp, 4, 4, 0, TABLE_TOP);  // 站在桌子上：说它离地多高
```

`over` 的第五个参数是**真实的离地高度**，不是「画在后面」的意思。如果一件家具
是照着地面建模的、却要摆在别的东西上，给 `lift` 是对的；如果抬高之后它变得不合
比例，改**模型**，不要改这个数 —— 桌灯就是这么处理的（见第 2 节）。

加一件「站在墙上的家具」（挂钟、窗帘、挂画之类）：在描述符里写 `cut: true`，
它就会跟着那面墙一起淡出；摆放时用 `wall(id, i, side)`，它会自己从模型的
占用标记里读出背面在哪，把背板贴到墙的内表面上。

调阳光轴：`src/main.js` 里的 `shaftAmount`（0 = 关掉，0.28 = 默认，往上更戏剧化），
体积分辨率在 `renderer.buildShaftVolume()`。

调遮挡：焦点在 `src/main.js` 的 `addFocus` / `addFocusBox` 那几行里，每帧重建。
想看它长什么样，`--lightdebug 9`；想知道某个像素到底被谁判成了挡路，
`--lightdebug 6`（幽灵层 alpha）和 `--lightdebug 8`（深度键）。
`game.focusOff = true` 可以在页面里直接关掉整个剖切，用来做 A/B 对照。
